## 先看結論：同一功能被叫很多次，不能直接叫重入

同一工作 `J17` 尚未完成，主掃描在 10、20 ms 再檢查它的狀態，這是**重複輪詢同一工作**；沒有第二個工作被建立，也沒有兩個執行區段同時持有同一實例。若新工作持續到達、服務只能一件一件完成，等待時間變長，這是**串行 FIFO 積壓**。`BEGIN` 與 `END` 在本例只代表一次函式呼叫的實際進入與返回；同一實例的 `BEGIN J17` 尚未返回，又有 `BEGIN J18` 進入，才有**呼叫重疊**的證據。這仍不證明任何資料已被覆寫，還需要讀寫位置、值與實例所有權的追蹤。

「等了 120 ms」也不能改寫成「CPU 忙了 120 ms」。下方模型把 120 ms 定義為合成的外部服務時間；它不做牆鐘等待，也不量測 PLC CPU 負載。CPU 看門狗、程式步驟等待和外部服務逾時各有不同證據；看門狗先看[任務執行超時、未啟動與缺資料](/articles/plc-watchdog-timeout-diagnosis)，單一步驟期限請看[5000 ms 等待與故障快照](/articles/plc-step-timeout-recovery)。

## 下載並重播固定 FIFO 案例

下載同一資料夾的 [模型](/examples/plc-backlog/backlog-model.mjs)、[固定輸入](/examples/plc-backlog/fixture.json)、[輸出程式](/examples/plc-backlog/run.mjs)、[獨立測試](/examples/plc-backlog/self-test.mjs) 和 [說明](/examples/plc-backlog/README.md)。需要 Node.js 22.13.0 以上，沒有 npm 套件、網站測試相依、PLC、網路或即時等待。

```powershell
node run.mjs
node --test self-test.mjs
```

固定輸入為八件工作：抵達時間 `0, 100, …, 700 ms`，單一服務者每件服務 `120 ms`，等候容量為 **2 件且不含正在服務的工作**。同一時間的規則明定為「先完成，再處理到達」。模型輸出每件已接受／拒絕的 `arrivalMs`、`startMs`、`finishMs`、`waitMs`；拒絕件的三個時間欄為 `null`，另保留拒絕前後的 `activeJobId`，可檢查拒絕沒有把正在服務的工作換掉。

此組八件都會接受，這正是容量 2 與完成優先順序下的可驗算答案：

| 工作 | 到達 | 開始 | 完成 | 等待 |
| ---- | ---: | ---: | ---: | ---: |
| J1   |    0 |    0 |  120 |    0 |
| J2   |  100 |  120 |  240 |   20 |
| J3   |  200 |  240 |  360 |   40 |
| J4   |  300 |  360 |  480 |   60 |
| J5   |  400 |  480 |  600 |   80 |
| J6   |  500 |  600 |  720 |  100 |
| J7   |  600 |  720 |  840 |  120 |
| J8   |  700 |  840 |  960 |  140 |

J7 在 600 ms 到達時，J5 已先完成、J6 已開始，因此它可使用空出的等候位置。這一個同時刻規則若改掉，整張時間表與容量判定都要重算。獨立測試另以 `0, 1, 2 ms`、服務 10 ms、等候容量 1 驗證 J3 被拒絕時，active 仍是 J1。

## 三份追蹤要得出三種不同答案

`fixture.json` 還有三份**合成**追蹤；不是任何 Q 系列 CPU 的實測或排程承諾。

| 追蹤                   | 可見列                                                                                      | 程式分類                      | 可以寫下的結論                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------- | ----------------------------- | ---------------------------------------------------------------------------- |
| `repeated-poll-j17`    | BEGIN J17 於 0、END J17 於 1；10、20 ms 只 POLL，外部工作到 120 ms 才完成                   | `REPEATED_POLL_SAME_WORK`     | 呼叫已返回；同一尚待外部完成的工作被多次檢查，沒有可見呼叫重疊               |
| `hypothetical-overlap` | main 的 BEGIN J17 後，interrupt 對同一 `requestState` BEGIN J18、END J18，最後 main END J17 | `OVERLAPPING_SHARED_INSTANCE` | 此合成資料顯示同一實例的呼叫重疊；它不證明資料已覆寫，也不是 QCPU 已觀察行為 |
| `missing-record`       | 有兩條 BEGIN，但標為 `traceComplete=false`                                                  | `INSUFFICIENT_EVIDENCE`       | 紀錄可能遺失；不把不完整列直接定為重入                                       |

實機追蹤至少要能列出工作 ID、實例 ID、入口、單調時間戳、事件種類（接受／BEGIN／END／POLL／外部完成／拒絕）、來源序號和遺失狀態。BEGIN／END 必須是實際函式呼叫的進入／返回，外部工作完成另記，不能用同一個 END 混寫。時間戳須為不倒退的安全整數；若來源是多個未同步時鐘，先保留時鐘來源與誤差，不能將它們排序後當作精確重疊。

## 平台資料不足時，先交付可填的證據表

這個小分類器採巢狀呼叫堆疊：後進入的呼叫須先返回。它不是多執行緒追蹤解析器，不能用它替跨核心、交錯返回的紀錄下結論。空資料、未知事件、錯配 END 或尚有未返回呼叫，都得到 INSUFFICIENT_EVIDENCE；完整資料沒有重疊、也沒有同一工作兩次 POLL，則只回 NO_OVERLAP_OBSERVED。fixture 的 traceComplete=true 是教材前提，實機必須另有遺失偵測證據支持。

本篇未核對特定 PLC 型號、韌體、程式類型或中斷設定的現行原廠手冊頁面，因此不宣稱任何 Q 系列排程、同因中斷保存或 FB 互斥行為。先以以下欄位把平台差異留在待驗證位置，再依**目標 CPU 型號、韌體和程式版本**查當前官方手冊與專案交叉參照。

| 欄位             | 現場應填內容                                    | 這一欄支持什麼判斷                 |
| ---------------- | ----------------------------------------------- | ---------------------------------- |
| 工作／實例／入口 | J 編號、FB 實例或資料區、main／週期／中斷等入口 | 是否真的是同一份共同狀態           |
| 接受／開始／結束 | 同一單調時基的時間、序號和來源                  | 排隊、等待或重疊的時間關係         |
| 拒絕             | 拒絕原因、等待容量、拒絕前後 active 工作        | 是否丟掉新工作而保持原工作         |
| 追蹤完整性       | 採樣週期、緩衝遺失、重啟與時鐘校正              | 能否從缺少 END 推論重入            |
| 平台依據         | 型號、韌體、程式類型、官方手冊連結與頁碼        | 該平台是否允許／延後／合併特定觸發 |

先在隔離副本加入追蹤，並量測加入前後的最大掃描時間。追蹤本身可能改變負載；若只有 HMI 每秒畫面，僅能說明該取樣時刻看見的狀態，不能證明毫秒級順序。真正變更拒絕、排隊、合併或重試前，還要由製程定義每筆請求能否丟失或合併，不能以一個 Busy 旗標取代資料契約。

## 可重現範例的範圍

範例會驗證：FIFO 容量、完成與到達同時的順序、拒絕時 active 不變、重複輪詢與共享實例**呼叫**重疊的差別，以及不完整資料停在「證據不足」。它不會驗證實機中斷、CPU 使用率、看門狗、設備回覆、資料覆寫或任何型號的排程規則。現場結論應回到最早一筆工作 ID／實例 ID／時間戳不一致處，再用目標平台文件與完整追蹤確認。
