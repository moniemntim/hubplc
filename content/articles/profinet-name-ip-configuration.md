## 名稱 IP與硬體角色分開

PROFINET裝置名稱、IP位址、控制器硬體配置與實際拓撲是四件不同的事。裝置名稱用於工程組態中的識別與啟動階段尋址；IP用於以太網路通訊；硬體配置描述控制器預期的模組與I/O；拓撲則是交換器、埠與線路的實體或管理關係。能ping到IP不代表I/O已建立。 這種分層也讓維修人員知道應先修網路身份還是先修I/O配置。 設備名稱變更後要重新確認控制器專案中的預期值，不能只看設備本地畫面。

先做資產表：每台設備記錄MAC、工程裝置名、目前IP、預期IP、控制器專案中的槽位與GSDML版本。MAC是現場辨識線索，不能拿來代替工程裝置名。若兩台設備使用相同名稱或IP，先隔離其中一台再修正，避免同時寫入造成不可判讀的結果。

GSDML描述設備與模組能力，控制器硬體配置則選擇實際插槽、子模組與參數；兩者匹配時才有機會建立Application Relationship。GSDML版本、設備韌體與工程工具支援範圍要一起核對，不能只因檔案能匯入就宣稱設備一定相容。

拓撲視圖可協助辨識鄰居與埠連線，但它不會自動修正所有IP或組態問題。LLDP提供鄰居資訊，對拓撲診斷有用；「IP全對」也不等於LLDP必須成功，更不等於I/O資料交換必然成功。每個結論都要對應到控制器診斷或設備狀態。

| 概念 | 回答的問題 | 不能直接推出 |
| --- | --- | --- |
| 裝置名 | 這台工程設備叫什麼 | I/O已交換 |
| IP | 封包往哪個網路端點走 | 名稱與配置正確 |
| GSDML/硬體 | 設備能力與槽位是否匹配 | 韌體必然相容 |
| 拓撲/LLDP | 鄰居與埠如何連接 | 應用關係已建立 |

## 從發現到AR建立的檢查順序

第一步在不改設備的情況下掃描或查閱現場清單，記錄MAC與目前名稱/IP；第二步用工程工具把唯一設備與專案中的預期名稱配對；第三步確認IP子網、閘道與控制器介面；第四步比對GSDML、韌體與硬體配置。每次只改一個變數並記錄時間，避免名稱、IP和模組同時變更。 變更前可匯出專案與設備清單，變更後以相同欄位逐項比對。 若網段含VLAN或管理交換器，連通性測試要注明測試來源埠與路徑。

假設設備MAC已知、目前IP為192.168.1.30，但專案預期裝置名是line1-io-03。能ping 192.168.1.30只證明該IP有回應；接著要確認設備實際名稱是否被指定、控制器配置的模組順序是否一致、AR與I/O狀態是否轉為正常。任何一步失敗都保留原診斷畫面。

若名稱遺失，先使用合規的設備識別方法確認MAC，不要以猜測名稱大量寫入網路。若名稱正確但AR不上線，查GSDML與硬體配置、模組參數、控制器介面及設備韌體。若AR正常但某子模組診斷錯誤，轉查槽位、I/O資料長度與通道參數，不要重新分配IP。

不同工程工具的畫面與步驟可能不同，因此本文使用「讀取、比對、設定、驗證」等通用動作，不提供虛構PLC指令。實際寫入裝置名稱或IP前，應依現場變更程序保存原始組態與回復方案；這是網路設備維護，不是靠ping就能完成的測試。

| 階段 | 證據 | 失敗時方向 |
| --- | --- | --- |
| 識別 | MAC與名稱唯一 | 查重複名稱/設備身份 |
| 網路 | IP、子網與連通性 | 查介面、VLAN、重複IP |
| 配置 | GSDML與槽位一致 | 查版本、模組、參數 |
| AR/I/O | 控制器與設備狀態正常 | 查診斷與資料長度 |

## 案例 同IP但資料交換失敗

案例一有兩台設備都被貼成192.168.1.30，工程人員從筆電ping到的回覆時有時無。第一個結論只能是IP衝突嫌疑，不能把回覆的MAC直接當成正確設備。先斷開其中一條支路，再逐台核對MAC、名稱與標籤，建立唯一資產表後才重新配置。 若設備重啟後結果改變，還要檢查名稱與參數是否被保存。 診斷清單最好保留修正前後兩份，方便確認問題是身份、配置還是鏈路。

案例二IP與名稱都正確，但控制器顯示AR建立失敗。此時比較專案選用的GSDML、設備韌體與實際模組；若配置多了一個子模組，資料長度或插槽可能不符。修正後要重新下載或套用組態，並以控制器與設備兩端的狀態證明恢復，不用ping取代。

案例三AR建立但某通道報診斷，拓撲圖也顯示鄰居。這代表名稱、IP與部分關係已可用，下一步查該槽位的模組型式、參數與I/O資料映射。LLDP正常只支持鄰居資訊，不會證明通道參數或應用資料正確。

每個案例的驗收紀錄要包含變更前後名稱/IP、設備MAC、GSDML版本、控制器專案版本、AR狀態、I/O狀態與時間。若只留一張ping截圖，無法追溯是哪個層級已成功，也無法安全地撤回錯誤變更。

## 拓撲與LLDP的限制

拓撲配置可以描述控制器、交換器與設備的鄰接關係，對名稱指派與線路診斷很有幫助，但實際支援取決於設備、交換器、韌體與工程工具。LLDP是鄰居發現機制，不是PROFINET所有應用資料交換的唯一必要條件；某設備未提供完整LLDP資訊時，仍要查AR與I/O診斷。 這能避免把鄰居發現畫面當成唯一的通訊證據。 若設備不支援某拓撲功能，將其記為不適用比猜測成錯誤更可靠。

當拓撲看似正確而AR失敗，先確認控制器介面與設備是否在同一預期網段，再查名稱、硬體配置和參數。不要一看到拓撲紅色就盲目改IP，也不要因IP能通就跳過GSDML和槽位核對。網路變更需逐項回復，避免讓多個未知同時存在。

驗收可設四個明確結果：設備身份唯一、名稱與專案一致、IP與網路規劃一致、AR及I/O狀態正常。拓撲和LLDP作為輔助證據另記錄；若某項能力不支援，尚未確認時填Unknown並查設備文件；已確認不支援則填不適用，不把缺少的鄰居資訊當成資料交換失敗。

未指定控制器型號、工程軟體版本、交換器型號與設備GSDML時，不能保證名稱設定畫面或診斷文字完全相同。本文只提供分層排查和驗收方法；真正下載、改名或切換運轉設備前，仍需依現場授權、備份與停機程序執行。

| 觀察 | 可支持的結論 | 仍需另查 |
| --- | --- | --- |
| ping成功 | IP端點有回應 | 名稱、AR、I/O |
| LLDP鄰居 | 鏈路鄰接資訊 | IP與應用資料 |
| AR正常 | 控制器關係已建立 | 各通道診斷 |
| I/O正常 | 目前資料交換可用 | 長期穩定與變更風險 |

## FAQ與來源

FAQ1：能ping到設備就代表PROFINET I/O正常嗎？答：不能。ping只證明某個IP有回應，仍要核對裝置名、GSDML、硬體配置、AR與I/O診斷。

FAQ2：裝置名和IP都正確但AR失敗，先改哪一個？答：不要盲改。先比對控制器配置、GSDML版本、韌體、模組槽位和參數，再依診斷證據一次改一項。

FAQ3：LLDP沒有完整鄰居資料是否一定不能交換資料？答：不一定。LLDP是拓撲與鄰居資訊來源，支援程度依設備與交換器而異；仍須直接查看AR與I/O狀態。

FAQ4：可以直接用通用PLC指令設定名稱或IP嗎？答：本文不提供虛構指令。名稱與IP設定方式依控制器、工程工具、設備韌體及現場程序而定，應查對應手冊。
