「沒回應」至少有三種不同情況：主站根本沒有送出請求、從站沒有送出回覆、回覆已在線上但主站沒有接受。先把故障定位到其中一段，再改一個條件驗證；同時換站號、鮑率、A/B、終端與重試次數，只會失去因果關係。

本文以 **Modbus RTU 跑在二線 RS-485** 為排查情境。RS-485 只描述電氣介面，不保證上層是 Modbus，也不決定任何設備的端子命名、終端阻值或通訊參數。以下範例是合成測試紀錄，沒有在實機硬體上執行或量測。

## 先建立可比較的單一交易

停用其他主站與非必要輪詢，只保留一個主站、一個從站與短暫的測試線路。選原廠 map 中已知可讀、沒有製程副作用的資料點，記下主站實際送出的 bytes，不要只記上位軟體畫面的輸入值。

| 欄位 | 合成範例，非設備預設 | 現場要填的依據 |
| --- | --- | --- |
| 上層協定 | Modbus RTU | 設備／PLC 手冊 |
| 從站位址 | 1 | 從站設定或面板 |
| UART 格式 | 9600、8E1 | 雙方通訊參數頁 |
| 測試讀取 | FC03、PDU 位址 0、1 register | 從站 map |
| 請求 PDU | `03 00 00 00 01` | 工具實際送出紀錄 |
| 逾時 | 有限且已記錄的值 | 從站最大回覆時間／現場規範 |

在 Modbus serial line 中，一次只能有一個 master 發起交易；一般從站位址為 1–247。位址 0 是廣播，從站不回覆，因此不能拿它當「讀取成功」的測試站號。這些規則見 Modbus Serial Line V1.02 §2.1、§2.2。[官方 PDF](https://www.modbus.org/file/secure/modbusoverserial.pdf)

## 依觀察結果走下一步

| 你看到的事實 | 先不要推論 | 下一個動作 | 結果如何縮小範圍 |
| --- | --- | --- | --- |
| 主站紀錄與 TX 端都沒有請求活動 | 不要先換線 | 查觸發條件、通道選擇、忙碌互鎖、通訊設定是否已下載 | 先證明主站真的嘗試傳送 |
| 有請求 bytes，線上沒有任何回覆活動 | 不要只加大逾時 | 核對從站供電／就緒、單播站號、協定、UART 格式、二線接法與極性 | 問題在從站接收前或從站未能處理請求 |
| 線上看得到回覆，但主站仍逾時 | 不要當成「從站沒回」 | 比對回覆站號、功能碼、長度、CRC、主站接收窗口與收發器方向切換 | 問題在回覆辨識或接收路徑 |
| 收到 `83 02` 或其他例外回覆 | 不要稱為沒有回應 | 依例外碼修正 FC、位址、數量或從站狀態 | 電氣與交易往返至少已成立 |
| 只有接回某一台或某段線後出錯 | 不要先認定終端壞了 | 一次加回一台／一段，查站號重複、拓撲、支線與該段接線 | 找出可重現的加入條件 |

TX／RX 燈只表示某種活動；它不提供 bytes、CRC 或站號。能擷取原始訊框時，保存時間戳、收發方向、UART 解碼設定與原始 hex；若只能看燈號，先把它當線索，不要當作通訊成功的證據。

## 從「有請求、無回覆」開始查

### 1. 核對請求本身

先對照從站文件確認：站號不是 0、功能碼受支援、PDU 位址使用正確的 0-based／顯示編號基準、數量未超限，且 UART 的鮑率、資料位元、同位與停止位元完全相同。每次只改一項並留下請求與結果。

例如合成範例的 `01 03 00 00 00 01 CRC` 是對站號 1 的 FC03 請求；它只有在該設備把位址 0 定義為可讀 Holding Register 時才有意義。改成 `00 ...` 是廣播，不應等待回覆；改成未支援的 FC 或非法位址，正常情況可能得到例外回覆，而不是有效數值。

功能碼、位址與例外回覆格式見 Modbus Application Protocol V1.1b3 §6.3、§7；位址 0 的廣播行為見 Serial Line V1.02 §2.2。[Application Protocol](https://www.modbus.org/file/secure/modbusprotocolspecification.pdf)；[Serial Line](https://www.modbus.org/file/secure/modbusoverserial.pdf)

### 2. 核對二線實體路徑，但不套用通用端子表

斷電、依現場程序確認可作業後，依**兩端該型號手冊**確認：介面是否啟用二線半雙工、兩個差動端子如何定義、訊號參考與隔離方式、線路是否連續。A/B、D+/D−、`+/-` 的字樣沒有跨品牌的固定配對；用端子真值表或原廠接線圖建立本案對照。

主站與從站都標「RS-485」仍可能使用不同的應用協定，或一端被設成四線／RS-422 模式。先確認模式和成對的 TX/RX 路徑，才談交換極性。若交換後出現回覆，也要回補兩端的定義與最終端子矩陣，不能只留下「A/B 對調」的口頭紀錄。

### 3. 只有在拓撲已知時檢查終端、偏壓與干擾

不要把「每台都加 120 Ω」當作排障步驟。終端值、是否內建、偏壓位置、訊號參考、屏蔽接地與隔離要求，取決於線纜、拓撲、設備收發器與現場電位差。先畫出實際幹線、兩個物理端點與支線，並查設備手冊已有的終端／偏壓設定；再依設計處理。

在斷電且外部路徑已排除的條件下，量到約 60 Ω 可能符合「兩個 120 Ω 終端並聯」的假設，但偏壓或內部電路可改變讀值。它只能用來發現可疑配置，不能獨自證明線路正確。若錯誤只在變頻器、馬達或特定設備動作時發生，保留該工況的時間與錯誤計數，再調查配線分離、共模、屏蔽與電源，而非先調大軟體重試。

## 有回覆卻仍逾時：檢查回覆是否可被接受

一筆可接受的 Modbus RTU 回覆，至少要對得上本次請求的站號、正常功能碼或功能碼加 `0x80` 的例外格式、預期長度及 CRC。不是每個「有波形」都是本次的回覆；可能是其他設備、延遲封包、碰撞或雜訊。

| 線上觀察 | 要比對的欄位 | 下一步 |
| --- | --- | --- |
| `01 03 02 00 64 CRC` | 站號 1、FC03、byte count 2、CRC | 再確認 `0064` 的型別／倍率；通訊往返已成立 |
| `01 83 02 CRC` | 站號 1、例外 FC `0x83`、exception 02、CRC | 查請求的 FC03 位址與連續範圍，不要再排查終端 |
| 回覆站號或 FC 不同 | 是否由另一站送出、是否收到舊封包 | 查重複站號、第二個主站或交易配對規則 |
| 長度或 CRC 不對 | 原始 bytes、UART 格式、收發方向、雜訊／碰撞 | 先保存擷取，再按一項條件做隔離測試 |

半雙工收發器的 transmit enable／receive enable 切換與主站接收邏輯，是設備或驅動程式的實作問題，沒有一組可套所有 PLC、USB-RS485 轉換器與從站的延遲值。若線上已有完整有效回覆卻主站判逾時，請查該主站的通道設定、接收緩衝、方向控制與逾時起算點。

## 別把 RTU 框架間隔當成設備回覆逾時

RTU 訊框以至少 3.5 個字元時間的靜默區隔；字元內間隔若超過 1.5 個字元時間，接收端可能把訊框視為不完整。當鮑率大於 19,200 bit/s，Serial Line V1.02 建議固定 `t1.5 = 750 µs`、`t3.5 = 1.75 ms`。這些是訊框判定時間，不是「從站必須在 1.75 ms 內回覆」的承諾。

回覆逾時要涵蓋從站處理、回覆傳輸、轉向與主站接收，應由設備文件與實測條件決定並設為有限值。前一筆完成或逾時前不要送下一筆，以免把回覆配錯請求。上述 timing 規則見 Serial Line V1.02 §2.5.1.1。[官方 PDF](https://www.modbus.org/file/secure/modbusoverserial.pdf)

## 用一份紀錄完成交接與驗收

| 每次測試必留的資料 | 為什麼需要 |
| --- | --- |
| 型號、port／通道、二線或四線模式、接線版本 | 別把另一通道或另一變型的設定混進來 |
| 站號、UART 格式、功能碼、PDU 位址與數量 | 可重建真正送出的要求 |
| 請求／回覆原始 hex、時間、擷取點 | 區分未送出、未回覆與未接受 |
| 本次只改的一個條件 | 讓結果可歸因 |
| 請求數、正常回覆、例外、逾時、CRC／長度錯誤 | 用統計而非一次成功判定 |

完成不應只寫「燈會閃」。在預先定義的觀察期間，確認每筆單播請求都有可對應的正常或例外回覆，正常值能與設備狀態核對，且錯誤計數符合現場驗收門檻。再逐台加回從站、支線與原本輪詢負載；只要錯誤重新出現，就回到最後一個新增條件。

本文沒有指定 QJ71C24N 或任何其他模組的端子短接、終端阻值、port 設定或逾時值，也未執行實機測試。這些值必須以實際型號文件與現場量測決定。
